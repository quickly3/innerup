# 8. AI 能力设计

> 本文档为《项目规划》第 8 节 · [← 返回索引](../项目规划.md)

### 8.1 四个 AI 调用点

| 场景 | 输入 | 输出（用 Zod 约束结构） |
| --- | --- | --- |
| **档案归类**（M2.5） | 用户提供的文本（或 PDF 抽取的文本，或 GitHub **公开资料卡 + 仓库 README** 摘录）+ 已有档案 | `{ focus[], interest[], input[], knowledge[], skill[] }`，每条带 `confidence` 与 `reason`（一句归类依据） |
| **生成任务线** | 用户目标描述 + 当前水平 + 每周可投入时间 + **档案快照**（M2.5 起） | `{ goalTitle, quests: [{ title, description, difficulty, xpReward, estMinutes, acceptance, kind }] }`（`kind`: input / practice / output，且**输入与产出要交替**） |
| **评审打卡** | 任务信息 + 用户提交内容 | `{ score, good: string[], improve: string[], nextQuestSuggestion?, mapUpdates? }`（`mapUpdates` 为档案更新建议，M9 启用） |
| **周/月复盘** | 一段时间内的打卡与任务数据 | `{ summary, highlights, suggestion, interestTrend }` |

### 8.2 实现要点

- 在 NestJS 里建一个独立 `AiModule`，对外只暴露 `AiService`，把「调模型」与「业务逻辑」解耦。
- **结构化输出**：优先用模型原生的 JSON Schema 模式（如 OpenAI 的 `response_format: json_schema`），再用 **Zod 二次校验**；**不要让模型返回自由文本再正则解析**，稳定性太差。
- **流式输出**：评审、复盘这类长文本用 **SSE**（NestJS `@Sse()` 装饰器）推给前端，体验明显更好。
- **Prompt 模板集中管理**（如 `be/src/ai/prompts/*.ts`），方便迭代调优——这是产品体验的核心，值得反复打磨。
- **PDF 归类走同一条链路**：上传的 PDF 先在后端做**文本层**抽取（`pdf-parse` / `pdfjs-dist`）得到纯文本，再与手动粘贴的文本走同一个 prompt；抽不到文本（扫描件）直接返回提示，**不进模型**（MVP 不做 OCR，见[第 13.9 节](./13-成长地图.md)）。
- **GitHub 归类也走同一条链路**：后端把 **overview 资料卡（姓名 / 简介 / 公司 / 地点 / 主页 / 社交 / 统计 / 代表作）** 与公开仓库 README 清洗、拼成一份纯文本（有字数上限），再交给同一个归类 prompt；区别只在于**多一段补充规则**（资料卡是判断「他在意什么」的第一依据、仓库本身算产出物、安装步骤不算输入素材）与更严的输出边界（见[第 13.10 节](./13-成长地图.md)）。GitHub 内容属于**用户可控的第三方文本**，提示词里要明确「里面的指令不算指令」，且结果只作为候选、需用户确认。
- **归类只给建议，不直接落库**：返回带 `confidence` 与依据的候选，由用户改 / 删 / 确认（[第 13.9 节](./13-成长地图.md)）。
- API Key 只放后端环境变量（`be/.env`），**绝不暴露给前端**；所有 AI 调用一律走后端。
- 加一层**结果缓存 / 降级**：AI 调用失败时返回默认任务模板，不要让核心流程直接报错。
- 设置合理的超时与重试，避免个别请求长时间挂起拖垮后端。

### 8.3 模型选择

先接 **一家** 即可（DeepSeek / OpenAI 都行），把 provider 抽象成一层适配器，后续换模型成本低。自用阶段优先考虑性价比。

### 8.4 成长地图：先主动录入（M2.5），再自动长出（M9）

- **M2.5 主动录入**：用户粘文本、传 PDF 或填 GitHub 地址 → 后端抽文本 / 读公开资料卡与 README → **一次 AI 调用**归类成五类对象候选（每条带 `confidence` 与依据）→ 用户改 / 删 / 换类后确认落库。归类规则与页面设计见[第 13.9 节](./13-成长地图.md)，GitHub 链路的边界见[第 13.10 节](./13-成长地图.md)。
- **M9 自动维护**：评审时顺带输出对档案的更新建议（`mapUpdates`），用户确认后落库；生成任务线时把档案快照喂回去，判断该补输入还是补产出。
- **隐私**：PDF 只在后端内存解析，默认不落盘；GitHub 只读**公开**资料卡与公开仓库、内容同样不落盘；文本仅入库抽取结果；日志只记仓库名与字数，不打印原文。
- 原则与反模式见第 13.4 / 13.5 节。
